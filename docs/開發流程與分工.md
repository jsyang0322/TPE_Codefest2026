## 二、AI token 的分配原則

1 號的 token 無限，其他四人有限。原則：**AI 用量大的工作集中給 1 號，其他人盡量做不太需要 AI 的工作。**

**交給 1 號：**

- 陌生技術的摸索：flutter_edge_ai、Gemma、Flutter 3.47／AGP 9 的建置錯誤。AI 的訓練資料可能比這些版本舊，需要反覆查文件、試錯，最花 token。
- 大量樣板程式，例如一次產生多個 Handler 或元件的骨架。
- PR 的 AI code review。
- 最後的 README 同步與檢查。

**不太需要雲端 AI 的工作（分給其他人）：**

- **prompt 調校：** 在手機上用裝置端模型測試，不花任何雲端 token。
- **資料整理：** 讀社會局網頁、找 data.taipei 資料集。
- **測試與排練：** 實機測試、飛航模式測試、demo 排練。

**token 有限的四位隊員，省 token 的做法：**

- **不用跟 AI 解釋專案。** AGENTS.md 會自動載入，裡面已經有規則和設計文件的位置。下指令時直接指名檔案和章節，例如「照 docs/系統設計文件.md 第三節的 `tts_speak` 規格，實作 `voice_message_handler.dart`」。
- **一個任務開一個新對話，做完就結束。** 對話越長，每次送出的內容越多。
- **錯誤訊息只貼相關的幾行**，不要貼整份 log。
- **只改需要改的部分。** 要 AI 改特定檔案的特定段落，不要整份重寫。
- **簡單修改自己動手**（改文字、調樣式），或改用較小的模型。

**AI 支援窗口：** 卡關超過 30 分鐘，或需要大量產生程式碼時，在群組丟給 1 號，附上檔案路徑、錯誤訊息和期望結果。1 號利用 App 建置的空檔處理。

**每個人都要看懂自己負責的程式。** 決選有評審問答。1 號幫忙產生的程式碼，要由負責人讀過再合併。

## 五、Git 流程

兩個 repo：本 repo（網頁、資料、文件）主要由 3、4、5 號修改；TownPass fork（App）主要由 1、2 號修改。

- **不直接 push 到 main。** 每個人開自己的分支，例如 `feat/llm`、`feat/voice`、`feat/web-ui`、`feat/agent-flow`、`data/senior-card`，用 PR 合併。
- **PR 要小、要常合併。** 開 PR 前先 `git pull --rebase origin main`；至少每 2–3 小時合併一次，避免最後一次大衝突。檢查點前把手上的 PR 合併完。
- **Review：** 1、2 號互相 review，3、4 號互相 review，5 號的 PR 由 3 號 review。比較大的 PR 再請 1 號跑 AI review。
- **Commit 訊息和 PR 說明不加 AI 共同作者行**（例如 `Co-Authored-By: Claude`）。團隊不希望 AI 出現在 GitHub Contributors。用 Claude Code 的人：AGENTS.md 已寫入這條規則；用其他工具的人，請確認工具不會自動加上。
- 模型檔、`.env` 不 commit。

容易衝突的檔案由負責人修改，其他人需要改時先跟負責人說：

| 檔案 | 負責人 |
| --- | --- |
| TownPass `pubspec.yaml`、`main.dart`、`tp_web_message_listener.dart` | 1、2 號都會改：各自只新增自己的行，不動別人的；衝突由 1 號處理 |
| TownPass `AndroidManifest.xml`、`Info.plist` | 2 |
| `web/src/bridge/`、`web/src/stores/` | 3（4 號需要新的 bridge 功能時跟 3 號說） |
| `README.md` | 5（1 號最後檢查） |

## 六、完成的定義

一項工作符合以下條件才算完成：

1. 已經透過 PR 合併進 main。
2. 在實機上可以運作；純網頁介面的工作，可以用瀏覽器 mock 驗證。
3. 執行時不呼叫任何雲端 AI。
4. 負責人說得出設計考量。
